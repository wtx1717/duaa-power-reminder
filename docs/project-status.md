# 项目状态总结

当前版本已经完成最基础的“定时查询后提醒”闭环，核心链路是可用的。

## 现在做到的事

1. 小程序支持微信登录、保存电表配置、手动查询电量、触发定时任务测试。
2. 云函数已经打通 `login`、`saveConfig`、`queryPower`、`scheduledCheck` 四个入口。
3. 定时任务会按电表维度去重查询，避免同一电表被多个用户重复请求。
4. 查询结果、提醒结果和任务锁都有对应的数据落库。
5. 当前调度策略已经有基础占位，但还比较简单，核心是保证流程先跑通。

## 目前的主要问题

1. 前端配置项还是偏多，用户现在需要填写照明电表、空调电表、阈值、查询时间和间隔。
2. 调度算法还没有围绕“目标用户规模下每日查询次数最少”做优化。
3. `planner.ts` 目前还是固定间隔思路，缺少基于历史数据的动态策略。

## 后续要做的方向

### 方向一：优化用户体验

目标是把前端收敛到“用户只需要绑定电表号码”。

建议继续做的事：

1. 减少表单字段，只保留必要的绑定信息。
2. 把阈值、调度间隔等策略参数收进后端默认值或自动策略。
3. 让用户更少参与配置，前端只负责绑定、查看状态和收提醒结果。

### 方向二：优化后端算法

目标是在满足提醒准确性的前提下，让目标用户规模下的每日查询次数尽量少。

建议继续做的事：

1. 基于 `power_records` 统计真实消耗速度，而不是固定 24 小时查询。
2. 根据剩余电量、近期消耗趋势、失败次数动态调整 `nextCheckAt`。
3. 按电表维度合并调度，继续保持“同一电表只查一次”。
4. 对低电量区间和异常区间设置更细的查询策略，平时降低频率，接近阈值时再收紧。

## 简短结论

当前项目已经完成最小可用版本，能实现定时查询和提醒。下一阶段重点应该从“把功能做出来”转到“把交互收窄”和“把调度做省”，这两个方向会直接决定后续的可用性和运行成本。
